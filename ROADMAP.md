# Roadmap to Production

Текущее состояние: **MVP с полным ядром бэкенда и рабочим фронтендом.** Ниже — сознательно зафиксированный техдолг, выявленные риски и пошаговый план движения к продакшен-релизу.

---

## Сознательно оставленный техдолг

Решения, принятые на этапе прототипирования осознанно, но требующие замены перед production:

### 1. JSON-персистентность вместо транзакционной БД

**Текущее состояние:** `TaskStore` хранит задачи в оперативной памяти Python-процесса и синхронизирует их с `backend/data/tasks.json` при каждом изменении. Состояние сохраняется между перезапусками, но JSON-файл не поддерживает транзакции — при одновременных запросах возможна потеря данных (race condition).

**Почему так:** на этапе MVP приоритет был на DAG-планировщик, MCP-инструменты и интеграцию LLM. JSON-персистентность — простейший способ сохранения данных без overhead'а настройки PostgreSQL, достаточный для одного пользователя.

**Что нужно:** PostgreSQL + SQLAlchemy / SQLModel + Alembic-миграции с ACID-транзакциями (`BEGIN → COMMIT / ROLLBACK`). Хранить `RawTask[]` и `project_start_date` в двух таблицах: `projects` и `tasks`.

### 2. Отсутствие WebSocket / SSE для стриминга LLM

**Текущее состояние:** запрос `POST /api/chat` — синхронный (с точки зрения клиента). Фронтенд ждёт полного ответа, показывая индикатор «Ассистент пересчитывает граф…». Промежуточные результаты (tool call → результат) не видны пользователю.

**Почему так:** реализация Tool Calling Loop внутри одного HTTP-запроса проще и надёжнее для MVP. Стриминг требует WebSocket-канала или SSE-эндпоинта с асинхронной отправкой промежуточных событий.

**Что нужно:** Server-Sent Events (SSE) для потоковой отправки: `event: tool_call` → `event: tool_result` → `event: reply`. Либо WebSocket с протоколом событий.

### 3. Клиентский Гантт без Canvas/SVG-виртуализации

**Текущее состояние:** `GanttChart.tsx` рендерит каждую задачу как DOM-элемент `<div>`. При 50 задачах это работает мгновенно. При 500 — начинает тормозить. При 5000 — неприемлемо.

**Почему так:** DOM-рендеринг проще для прототипа, позволяет использовать стандартные React-паттерны (onClick, условный рендеринг) и полностью достаточен для демонстрации.

**Что нужно:** переход на Canvas или SVG с виртуальным скроллингом (рендерить только видимые строки). Библиотеки-кандидаты: `react-virtualized`, `@tanstack/virtual`, или кастомный Canvas-движок.

### 4. Отсутствие аутентификации и multi-tenancy

**Текущее состояние:** любой, кто знает URL бэкенда, может читать и мутировать задачи. Нет понятия «пользователь» или «проект».

**Почему так:** на этапе прототипа проект — одиночный черновик без разделения по пользователям.

**Что нужно:** JWT-аутентификация, OAuth2 (Google/GitHub), разделение данных по `user_id` / `project_id`.

### 5. Отсутствие роутинга LLM-провайдеров

**Текущее состояние:** клиент `llm_client.py` работает с одной моделью, указанной в `LLM_MODEL`. При недоступности провайдера (отсутствие баланса, ошибка API) — запросы падают.

**Почему так:** на этапе MVP достаточно одной стабильной модели (DeepSeek через OpenRouter). Роутинг усложняет логику и требует механизма обнаружения ошибок, retry-логики и fallback-моделей.

**Что нужно:** 
- Конфигурация fallback-провайдеров: `LLM_MODELS=["deepseek/deepseek-chat", "openai/gpt-4o-mini", "google/gemini-2.0-flash-exp"]`
- Автоматический переключатель при ошибках API (429, 503, отсутствие баланса)
- Логгирование переключений: какая модель сработала, какая упала, время ответа
- Health-check эндпоинт для диагностики доступности моделей

### 6. Отсутствие обработки больших таблиц и RAG-поиска

**Текущее состояние:** все задачи проекта (`RawTask[]`) передаются в контекст LLM целиком через системный промпт. Это работает до ~100–200 задач, дальше — упирается в контекстное окно модели (128K токенов).

**Почему так:** прототип сфокусирован на управлении малыми и средними проектами (5–50 задач), где полный контекст умещается в один промпт.

**Что нужно:**
- Векторизация задач (Embedding через OpenAI API / open-source модели)
- Поиск по семантическому сходству (ChromaDB / Qdrant / pgvector)
- Передача в LLM только релевантных задач (Top-K по косинусному расстоянию)
- Тестирование на проектах 1000–2000 задач

## Риски и порядок закрытия

### Фаза 0: Security Hardening (приоритет: критический)

**Без этого невозможен публичный доступ к приложению.**

- **Security audit кода:**
  - Запуск Bandit (Python) + npm audit (JavaScript) для выявления известных уязвимостей
  - Проверка зависимостей на CVE (Common Vulnerabilities and Exposures)
  - Статический анализ кода на SQL Injection, XSS, CSRF, Path Traversal
- **Секреты и переменные окружения:**
  - Переместить все API-ключи из `.env` в защищённое хранилище (Vault, AWS Secrets Manager, GitHub Secrets для CI/CD)
  - Добавить `.env` в `.gitignore` (уже есть, но проверить, что файл не коммитился в историю)
  - Ротация ключей: процедура обновления `LLM_API_KEY`, `GEMINI_API_KEY` без простоя сервиса
- **HTTPS и сертификаты:**
  - Настроить Let's Encrypt с автообновлением сертификатов (через Certbot или Traefik)
  - Редирект HTTP → HTTPS на уровне Nginx / Traefik
  - HSTS-заголовки (Strict-Transport-Security) для принудительного HTTPS
- **CORS и CSP:**
  - Ограничить `allow_origins` в FastAPI только разрешёнными доменами (убрать `*`)
  - Добавить CSP-заголовки (Content Security Policy) для защиты от XSS
- **Rate Limiting:**
  - Middleware на FastAPI для ограничения запросов на `/api/chat` (например, 10 запросов/минуту на IP)
  - Nginx rate limiting на уровне reverse proxy
- **Input Validation:**
  - Проверка всех входных данных через Pydantic (уже есть, но усилить валидацию длин строк, диапазонов чисел)
  - Защита от массивных JSON-payload (лимит размера тела запроса: 10MB)
- **CSRF-защита:**
  - Добавить CSRF-токены на мутирующих эндпоинтах (`POST /api/chat`, `POST /api/tasks/upload`, `PUT /api/tasks/sync`)
  - Или использовать SameSite-куки для защиты от CSRF (при JWT-аутентификации)

**Риск:** без этих мер приложение уязвимо к XSS, CSRF, DDoS, утечке ключей API. Любая публикация в интернете без security hardening — прямая угроза безопасности пользователей и инфраструктуры.

### Фаза 1: Персистентность и мультитенантность (приоритет: критический)

**Без этого невозможен ни один production use-case с несколькими пользователями.**

- **Миграция на PostgreSQL:**
  - Добавить SQLModel / SQLAlchemy модели (`Project`, `Task`, `User`) с полями, зеркалирующими `RawTask`
  - Настроить Alembic для автоматических миграций схемы БД
  - Заменить `TaskStore._raw_tasks: list` на ORM-запросы с сохранением транзакционности (через `async with session.begin()`)
  - Сохранить seed-данные как Alembic data migration (первая миграция добавляет 5 демо-задач для нового пользователя)
- **Аутентификация (JWT + OAuth2):**
  - FastAPI Users или ручная JWT-имплементация
  - Middleware: `Depends(get_current_user)` на protected-роутах
  - OAuth2 через Google / GitHub для регистрации и логина
- **Авторизация (RBAC):**
  - Роли: Owner (полный доступ), Editor (редактирование задач), Viewer (только чтение)
  - Проверка прав на уровне эндпоинтов: `Depends(require_permission("edit"))`
- **Multi-tenancy:**
  - Изоляция: все запросы к TaskStore получают `user_id` / `project_id`
  - Таблица `projects`: `id`, `owner_id`, `name`, `start_date`, `created_at`
  - Таблица `tasks`: внешний ключ `project_id` для изоляции задач по проектам
  - Индексы на `user_id`, `project_id` для быстрого поиска
- **Бэкапы PostgreSQL:**
  - Автоматические бэкапы ежедневно (pg_dump + cron)
  - Point-in-time recovery (WAL-архивирование) для восстановления на любой момент времени
  - Тестирование восстановления из бэкапа (раз в месяц)

**Риск:** изменение API TaskStore может затронуть `mcp_server.py` и `routers/chat.py` — эти модули потребляют `store.get_raw_tasks()` / `store.set_raw_tasks()`. Сигнатуры должны сохраниться, реализация станет async. При добавлении пользователей модель `GanttTask` получит поле `owner_id` — нужно обновить оба контракта (Zod + Pydantic) и не сломать LLM Tool Calling (инструменты не должны принимать `owner_id` от LLM).

### Фаза 2: Масштабирование и оптимизация (приоритет: высокий)

**Без этого UX страдает при росте числа задач и медленных ответах LLM.**

- **SSE-стриминг LLM:**
  - Эндпоинт `GET /api/chat/stream` с `text/event-stream`
  - События: `tool_call_started`, `tool_call_completed`, `reply_chunk`, `reply_done`
  - Фронтенд: `EventSource` с реактивным обновлением сообщений
  - Пересмотр `_run_tool_calling_loop` — цикл должен стать асинхронным генератором (`async for event in loop`), а не одномоментным `return`
- **Canvas-Гантт (виртуализация UI):**
  - Рендеринг баров задач на Canvas с виртуальным окном
  - Прокрутка и зум (mouse wheel)
  - SVG как fallback для статического экспорта
  - Тестирование на проектах 500+ задач
- **Роутинг LLM-провайдеров:**
  - Конфигурация fallback-моделей: `LLM_MODELS=["deepseek/deepseek-chat", "openai/gpt-4o-mini", "google/gemini-2.0-flash-exp"]`
  - Механизм retry с автопереключением на следующую модель при ошибке (429, 503, отсутствие баланса)
  - Логгирование переключений: timestamp, fallback_reason, model_from, model_to, latency
  - Health-check эндпоинт `/api/health/llm` для диагностики статуса моделей
- **RAG для больших таблиц (1000–2000 задач):**
  - Векторизация задач: Embedding через OpenAI API (`text-embedding-3-small`) или open-source модели (Sentence-Transformers)
  - Векторная БД: ChromaDB (локально), Qdrant (production), или pgvector (расширение PostgreSQL)
  - Поиск по семантическому сходству: Top-K (K=20–50) задач по косинусному расстоянию к запросу пользователя
  - Передача в LLM только релевантных задач вместо всего массива
  - Тестирование на проектах 2000 строк: время ответа, качество поиска, точность мутаций
- **Кэширование частых запросов (Redis):**
  - Кэш для `/api/tasks` (список задач с датами) с TTL 60 секунд
  - Кэш для LLM-ответов на повторяющиеся вопросы (опционально, требует хеширования промптов)
  - Инвалидация кэша при мутациях (`POST /api/chat`, `PUT /api/tasks/sync`)
- **Очередь фоновых задач (Celery + Redis / RabbitMQ):**
  - Асинхронная обработка длительных операций: импорт больших Excel-файлов (1000+ строк), экспорт PDF/PNG
  - Фоновые задачи: отправка Email-уведомлений, генерация отчётов, векторизация задач
  - Мониторинг очереди: Flower (веб-UI для Celery)

**Риск:** SSE требует пересмотра `_run_tool_calling_loop` — цикл должен стать асинхронным генератором. Canvas-рендеринг может сломать существующий UI — потребуется полная переработка `GanttChart.tsx`. RAG добавляет сложность: векторизация может быть медленной, поиск может пропустить нужные задачи (ложные отрицания).

### Фаза 3: UX и дополнительные функции (приоритет: средний)

**Улучшения UX, не критичные для запуска, но важные для retention пользователей.**

- **Голосовой ввод (Whisper API):**
  - Кнопка микрофона в `ChatPanel.tsx`
  - Запись аудио через `MediaRecorder API`
  - Отправка на `/api/chat/transcribe` → Whisper API → текст → обработка как обычный запрос
  - Поддержка русского и английского языков
- **Календарный UI для дат (Datepicker):**
  - В модальном окне `TaskDetailModal.tsx` заменить текстовый ввод дат на React Datepicker
  - Визуальный выбор дат с подсветкой выходных и праздников
  - Валидация: дата начала не может быть позже даты окончания
- **Экспорт в дополнительные форматы:**
  - PDF (через `jsPDF` или бэкенд на Python: `reportlab` / `WeasyPrint`)
  - PNG-скриншот диаграммы Гантта (через Canvas → `toBlob()`)
  - iCal-формат для импорта в Google Calendar / Outlook
- **Email-уведомления о дедлайнах:**
  - Cron-задача (ежедневно в 9:00): проверка задач, заканчивающихся через 1–3 дня
  - Отправка Email через SendGrid / AWS SES / SMTP
  - Настройки уведомлений: пользователь может включить/отключить, выбрать дни до дедлайна
- **Push-уведомления (Web Push API):**
  - Service Worker для регистрации push-подписки
  - Backend: отправка уведомлений через VAPID (Web Push Protocol)
  - Уведомления о завершении фоновых задач (импорт большого Excel-файла)

**Риск:** Whisper API платный ($0.006 за минуту аудио) — может быть дорого при масштабе. Datepicker может конфликтовать с существующей валидацией дат. Email-уведомления требуют настройки SMTP и обработки отказов (bounces).

### Фаза 4: DevOps и мониторинг (приоритет: критический для production)

**Без этого невозможна стабильная работа и быстрое реагирование на инциденты.**

- **CI/CD пайплайн (GitHub Actions):**
  - Этап 1 (Lint): Ruff (Python) + ESLint (TS) + Prettier
  - Этап 2 (Test): pytest (backend) + Vitest (frontend)
  - Этап 3 (Build): Docker-образы (backend + frontend)
  - Этап 4 (Deploy): развертывание на staging → ручная проверка → deploy на production
  - Blue-Green deployment или Canary deployment для минимизации downtime
- **Мониторинг (Prometheus + Grafana):**
  - Метрики Uvicorn: RPS (requests per second), латентность (p50, p95, p99), ошибки (5xx)
  - Метрики PostgreSQL: количество соединений, размер БД, медленные запросы
  - Метрики Redis: hit rate, memory usage
  - Метрики LLM: время ответа, количество токенов, стоимость запроса, ошибки API
  - Дашборд в Grafana с alerting (Slack / Email при превышении порогов)
- **Централизованное логирование (ELK / Loki):**
  - Сбор логов с всех инстансов бэкенда в Elasticsearch / Loki
  - Структурированные логи (JSON) через structlog
  - Kibana / Grafana для поиска и фильтрации логов
  - Retention policy: хранить логи 30 дней (горячие данные), 365 дней (холодные данные в S3)
- **Трейсинг (OpenTelemetry / Jaeger):**
  - Распределённая трассировка запросов: фронтенд → FastAPI → PostgreSQL → LLM
  - Trace ID: сквозной идентификатор для отслеживания запроса через все сервисы
  - Анализ узких мест (bottlenecks): какой сервис самый медленный
- **Alerting (Sentry + PagerDuty):**
  - Sentry для автоматической отправки ошибок Python и JavaScript
  - PagerDuty для критических инцидентов: downtime бэкенда, превышение latency, ошибки БД
  - On-call ротация: кто дежурный инженер на текущей неделе
- **Балансировщик нагрузки (Nginx / HAProxy):**
  - Round-robin распределение запросов между несколькими воркерами FastAPI
  - Health-check эндпоинт `/api/health` для автоматического исключения упавших воркеров
  - Session affinity (опционально): один пользователь всегда попадает на один воркер
- **Горизонтальное масштабирование:**
  - Kubernetes-кластер (или Docker Swarm): автоскейлинг воркеров FastAPI при нагрузке
  - PostgreSQL: master-slave репликация (read replicas для чтения, master для записи)
  - Redis Cluster для отказоустойчивости кэша
- **Disaster Recovery Plan:**
  - Runbook: инструкции по восстановлению после полного падения кластера
  - Резервный дата-центр (multi-region deployment) для катастроф (пожар, наводнение)
  - RTO (Recovery Time Objective): целевое время восстановления < 1 час
  - RPO (Recovery Point Objective): допустимая потеря данных < 5 минут

**Риск:** настройка Kubernetes сложна — требует DevOps-экспертизы. Мониторинг генерирует большой объём данных — нужен storage для метрик и логов. Alerting может генерировать false positives — потребуется тюнинг порогов.

### Фаза 5: Тестирование и качество кода (приоритет: высокий)

**Без этого невозможна уверенность в корректности и стабильности системы.**

- **Покрытие тестами (≥80%):**
  - pytest-cov для измерения покрытия кода тестами
  - Цель: ≥80% покрытия для `backend/app/services/`, `backend/app/routers/`, `backend/app/mcp_server.py`
  - Игнорировать `__init__.py`, `main.py`, логгеры
- **Интеграционные тесты (pytest + TestClient):**
  - Тесты для всех эндпоинтов: `GET /api/tasks`, `POST /api/chat`, `POST /api/tasks/upload`, `GET /api/tasks/export`
  - Проверка кодов ответа (200, 400, 422), структуры JSON, валидации ошибок
  - Тесты на edge cases: пустой проект, цикл зависимостей, несуществующий task_id
- **Фронтенд-тесты (React Testing Library + Vitest):**
  - Юнит-тесты для компонентов: `GanttChart.tsx`, `ChatPanel.tsx`, `FileUpload.tsx`
  - Проверка рендеринга, обработки ошибок (ZodError), обработки событий (onClick, onChange)
  - Моки для API-запросов (`fetch` через `vitest.mock()`)
- **E2E-тесты (Playwright / Cypress):**
  - Сценарий 1: загрузка Excel → проверка рендеринга Гантта → скачивание Excel
  - Сценарий 2: отправка сообщения в чат → проверка ответа LLM → обновление задач
  - Сценарий 3: создание задачи через чат → проверка появления на диаграмме
  - Запуск E2E в CI/CD перед деплоем на production
- **Нагрузочное тестирование (Locust / k6):**
  - Сценарий: 1000 одновременных пользователей → каждый отправляет 10 запросов `/api/chat`
  - Измерение: RPS, латентность (p50, p95, p99), процент ошибок
  - Цель: RPS ≥ 100, p95 < 2 секунды, процент ошибок < 1%
  - Тестирование на staging перед каждым major-релизом
- **Линтеры и форматтеры:**
  - Ruff (Python): линтер + форматтер (заменяет flake8 + black)
  - ESLint (TypeScript): правила AirBnB или Standard
  - Prettier (TypeScript): авто-форматирование кода
  - Pre-commit hooks: запуск линтеров перед каждым коммитом
- **Автоматизация тестирования:**
  - GitHub Actions: запуск всех тестов (юнит, интеграционные, E2E) при каждом pull request
  - Запрет мержа PR без прохождения тестов и линтеров
  - Покрытие кода должно быть ≥80% — иначе CI падает

**Риск:** E2E-тесты хрупкие — могут ломаться при изменении UI. Нагрузочное тестирование требует отдельного окружения (staging) и ресурсов. Линтеры могут замедлить разработку (требуется настройка правил).

## Что НЕ входит в Roadmap (out of scope)

- **Мобильное приложение (React Native / Flutter)** — фокус на веб-версии.
- **Real-time коллаборация** (несколько пользователей редактируют один проект одновременно) — требует WebSocket + CRDT для синхронизации конфликтов.
- **Интеграция с Jira / Trello / Asana** (импорт/экспорт через API) — можно добавить как плагинную систему после запуска.
- **Авто-ресурсное планирование** (назначение исполнителей с учётом загрузки, конфликтов календаря) — требует календарного API (Google Calendar / Outlook) и алгоритмов оптимизации (linear programming).
- **Плагинная система для кастомных MCP-инструментов** — пользователь может добавлять свои инструменты через Python-код. Требует песочницы (sandbox) для безопасного выполнения стороннего кода.
- **Графический редактор Гантта** (drag-and-drop баров для изменения дат) — противоречит архитектурному инварианту №1 (даты вычисляет только DAG Scheduler). Реализация потребует пересмотра core-логики: drag должен транслироваться в изменение `duration_days` и `predecessors`, а не прямое редактирование дат.
- **Версионирование проектов (Git-like history)** — откат к предыдущим состояниям проекта, бранчи, мерджи. Требует версионирования данных (каждое изменение — новая версия) и diff-алгоритмов для визуализации изменений.

### Технические риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| **Race condition в TaskStore (JSON-файл)** | Высокая | Потеря данных | Миграция на PostgreSQL с транзакциями (Фаза 1) |
| **Падение LLM-провайдера (нет баланса, ошибка API)** | Средняя | Полный отказ чата | Роутинг с fallback-моделями (Фаза 2) |
| **Упирание в контекст LLM (проекты 1000+ задач)** | Высокая при масштабе | Ошибка API, высокая стоимость | RAG + векторный поиск (Фаза 2) |
| **UI лагает на проектах 500+ задач (DOM-рендеринг)** | Высокая при масштабе | Плохой UX | Canvas + виртуализация (Фаза 2) |
| **Утечка API-ключей (коммит .env в Git)** | Средняя | Кража ключей, финансовые потери | `.env` в `.gitignore`, Vault, Git history rewrite (Фаза 0) |
| **XSS / CSRF атаки** | Низкая (React экранирует) | Кража токенов, несанкционированные действия | CSP-заголовки, CSRF-токены (Фаза 0) |
| **SQL Injection при миграции на PostgreSQL** | Низкая (SQLAlchemy ORM) | Утечка данных, модификация БД | Параметризованные запросы, code review (Фаза 1) |
| **DDoS атака (нет rate limiting)** | Средняя | Перегрузка сервера, downtime | Rate limiting middleware (Фаза 0) |
| **Циклическая зависимость в графе задач** | Низкая (есть защита) | Ошибка расчёта дат | DFS-проверка циклов (уже есть в scheduler.py) |
| **Ошибка DAG Scheduler (неверные даты)** | Низкая | Неправильное расписание | Snapshot-тесты на eval-кейсах (уже есть в tests/) |

### Организационные риски

| Риск | Вероятность | Влияние | Митигация |
|---|---|---|---|
| **Нехватка DevOps-экспертизы (Kubernetes, Prometheus)** | Высокая | Задержка запуска, нестабильность | Найм DevOps-инженера или переход на managed-сервисы (AWS ECS, GCP Cloud Run) |
| **Высокая стоимость LLM-запросов при масштабе** | Средняя | Финансовые потери | Переход на дешёвые модели (DeepSeek), кэширование ответов, rate limiting |
| **Отсутствие бюджета на мониторинг (Datadog, New Relic)** | Средняя | Слепое управление, медленное реагирование | Open-source альтернативы (Prometheus + Grafana, Sentry free tier) |
| **Юридические риски (GDPR, хранение персональных данных)** | Средняя (при запуске в EU) | Штрафы | Политика конфиденциальности, согласие на обработку данных, анонимизация логов |
| **Недостаток тестов при быстрой разработке** | Высокая | Баги в production, downtime | Обязательное прохождение CI/CD, запрет мержа без тестов (Фаза 5) |

## Приложение: Детализация компонентов

### A. PostgreSQL-схема (целевая)

```sql
-- Таблица пользователей (аутентификация)
CREATE TABLE users (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    email VARCHAR(255) UNIQUE NOT NULL,
    hashed_password VARCHAR(255) NOT NULL,  -- bcrypt
    full_name VARCHAR(255),
    is_active BOOLEAN DEFAULT TRUE,
    created_at TIMESTAMP DEFAULT NOW()
);

-- Таблица проектов (multi-tenancy)
CREATE TABLE projects (
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    owner_id UUID REFERENCES users(id) ON DELETE CASCADE,
    name VARCHAR(255) NOT NULL,
    start_date DATE NOT NULL DEFAULT CURRENT_DATE,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

-- Таблица задач (основные данные)
CREATE TABLE tasks (
    id VARCHAR(50) PRIMARY KEY,  -- task-1, task-2, ...
    project_id UUID REFERENCES projects(id) ON DELETE CASCADE,
    title VARCHAR(255) NOT NULL,
    description TEXT DEFAULT '',
    assignee VARCHAR(255) DEFAULT '',
    duration_days INTEGER NOT NULL CHECK (duration_days >= 1),
    predecessors TEXT[],  -- массив task_id
    preferred_start_date DATE,
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW()
);

-- Индексы для быстрого поиска
CREATE INDEX idx_tasks_project_id ON tasks(project_id);
CREATE INDEX idx_projects_owner_id ON projects(owner_id);

-- Таблица ролей (RBAC)
CREATE TABLE project_members (
    project_id UUID REFERENCES projects(id) ON DELETE CASCADE,
    user_id UUID REFERENCES users(id) ON DELETE CASCADE,
    role VARCHAR(50) NOT NULL CHECK (role IN ('owner', 'editor', 'viewer')),
    PRIMARY KEY (project_id, user_id)
);
```
