# Roadmap to Production

Текущее состояние: **MVP с полным ядром бэкенда и рабочим фронтендом.** Ниже — сознательно зафиксированный техдолг и пошаговый план движения к продакшен-релизу.

---

## Сознательно оставленный техдолг

Решения, принятые на этапе прототипирования осознанно, но требующие замены перед production:

### 1. In-Memory TaskStore

**Текущее состояние:** `TaskStore` хранит задачи в оперативной памяти Python-процесса. При перезапуске `uvicorn` состояние теряется, загружаются seed-данные.

**Почему так:** на этапе MVP приоритет был на DAG-планировщик, MCP-инструменты и интеграцию LLM. Персистентность добавляет слой абстракции (ORM, миграции), не влияя на корректность ядра, и была отложена осознанно.

**Что нужно:** PostgreSQL + SQLAlchemy / SQLModel + Alembic-миграции. Хранить `RawTask[]` и `project_start_date` в двух таблицах: `projects` и `tasks`.

### 2. Отсутствие WebSocket / SSE для стриминга LLM

**Текущее состояние:** запрос `POST /api/chat` — синхронный (с точки зрения клиента). Фронтенд ждёт полного ответа, показывая индикатор «Ассистент пересчитывает граф…». Промежуточные результаты (tool call → результат) не видны пользователю.

**Почему так:** реализация Tool Calling Loop внутри одного HTTP-запроса проще и надёжнее для MVP. Стриминг требует WebSocket-канала или SSE-эндпоинта с асинхронной отправкой промежуточных событий.

**Что нужно:** Server-Sent Events (SSE) для потоковой отправки: `event: tool_call` → `event: tool_result` → `event: reply`. Либо WebSocket с протоколом событий.

### 3. Клиентский Гантт без Canvas/SVG-виртуализации

**Текущее состояние:** `GanttChart.tsx` рендерит каждую задачу как DOM-элемент `<div>`. При 50 задачах это работает мгновенно. При 500 — начинает тормозить. При 5000 — неприемлемо.

**Почему так:** DOM-рендеринг проще для прототипа, позволяет использовать стандартные React-паттерны (onClick, условный рендеринг) и полностью достаточен для демонстрации.

**Что нужно:** переход на Canvas или SVG с виртуальным скроллингом (рендерить только видимые строки). Библиотеки-кандидаты: `react-virtualized`, `@tanstack/virtual`, или кастомный Canvas-движок.

### 4. Отсутствие аутентификации и multi-tenancy

**Текущее состояние:** любой, кто знает URL бэкенда, может читать и мутировать задачи. Нет понятия «пользователь» или «проект».

**Почему так:** на этапе прототипа проект — одиночный черновик без разделения по пользователям.

**Что нужно:** JWT-аутентификация, OAuth2 (Google/GitHub), разделение данных по `user_id` / `project_id`.

## Чего не хватает для Production

| Компонент | Текущее состояние | Целевое состояние |
|---|---|---|
| **База данных** | In-Memory | PostgreSQL + SQLAlchemy / SQLModel |
| **Миграции** | Отсутствуют | Alembic |
| **Аутентификация** | Отсутствует | JWT + OAuth2 (FastAPI Users) |
| **Авторизация** | Отсутствует | RBAC: владелец / редактор / зритель |
| **Multi-tenancy** | Одно глобальное состояние | Проекты с изоляцией по `user_id` |
| **Стриминг LLM** | Синхронный POST /api/chat | SSE или WebSocket |
| **Rate limiting** | Отсутствует | Middleware на FastAPI или nginx |
| **UI-виртуализация Гантта** | DOM на всех задачах | Canvas/SVG с виртуальным скроллингом |
| **Тесты (юнит / интеграционные)** | Смоук-скрипты | pytest + React Testing Library |
| **CI/CD** | Отсутствует | GitHub Actions: линтер → тесты → деплой |
| **Логирование** | print / traceback | structlog / loguru + Sentry |
| **Мониторинг** | Отсутствует | Prometheus + Grafana / Uvicorn metrics |
| **Контейнеризация** | Ручной запуск | Docker Compose (backend + frontend + DB) |
| **Секреты** | .env-файл | Vault / sealed secrets / CI env vars |
| **Документация API** | Auto-generated OpenAPI (FastAPI) | + описание ошибок и примеров запросов |

## Риски и порядок закрытия

### Фаза 1: Персистентность (приоритет: критический)

**Без этого невозможен ни один production use-case.**

- Добавить SQLModel / SQLAlchemy модели (`Project`, `Task`) с полями, зеркалирующими `RawTask`.
- Настроить Alembic для автоматических миграций.
- Заменить `TaskStore._raw_tasks: list` на ORM-запросы с сохранением транзакционности (через `async with session.begin()`).
- Сохранить seed-данные как Alembic data migration (первая миграция добавляет 5 демо-задач).
- **Риск:** изменение API TaskStore может затронуть `mcp_server.py` и `routers/chat.py` — эти модули потребляют `store.get_raw_tasks()` / `store.set_raw_tasks()`. Сигнатуры должны сохраниться, реализация станет async.

### Фаза 2: Авторизация и лимиты (приоритет: высокий)

**Без этого невозможен многопользовательский доступ.**

- FastAPI Users или ручная JWT-имплементация.
- Middleware: `Depends(get_current_user)` на protected-роутах.
- Изоляция: все запросы к TaskStore получают `user_id` / `project_id`.
- Rate limiting: middleware с ограничением запросов на пользователя/токен для `/api/chat`.
- **Риск:** при добавлении пользователей модель `GanttTask` получит поле `owner_id` — нужно обновить оба контракта (Zod + Pydantic) и не сломать LLM Tool Calling (инструменты не должны принимать `owner_id` от LLM).

### Фаза 3: Оптимизация UI и SSE-стриминг (приоритет: средний)

**Без этого UX страдает при росте числа задач и медленных ответах LLM.**

- **SSE-стриминг:** эндпоинт `GET /api/chat/stream` с `text/event-stream`. События: `tool_call_started`, `tool_call_completed`, `reply_chunk`, `reply_done`. Фронтенд: `EventSource` с реактивным обновлением сообщений.
- **Canvas-Гантт:** рендеринг баров задач на Canvas с виртуальным окном. Прокрутка и зум (mouse wheel). SVG как fallback для статического экспорта.
- **Риск:** SSE требует пересмотра `_run_tool_calling_loop` — цикл должен стать асинхронным генератором (`async for event in loop`), а не одномоментным `return`.

## Что НЕ входит в Roadmap (out of scope)

- Мобильное приложение (React Native).
- Real-time коллаборация (несколько пользователей редактируют один проект одновременно — требует WebSocket + CRDT).
- Интеграция с Jira / Trello / Asana (импорт/экспорт через API).
- Авто-ресурсное планирование (назначение исполнителей с учётом загрузки).
- Плагинная система для кастомных MCP-инструментов.
