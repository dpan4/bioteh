## Обзор

AI-Native Gantt Chart — это веб-приложение, в котором диаграмма Гантта является не просто визуализацией, а живым объектом, управляемым AI. Вы говорите ассистенту «увеличь длительность разработки API до 10 дней» — и задачи пересчитываются с учётом графа зависимостей. Вы загружаете Excel-файл со списком задач — и получаете готовое расписание за секунды.

**Ключевые компоненты:**

- **DAG Scheduler** — ядро планирования: топологическая сортировка (алгоритм Кана), математический расчёт всех дат, обнаружение и блокировка циклических зависимостей.
- **LLM Tool Calling Loop** — 5-раундовый цикл, в котором LLM через OpenRouter (или любой OpenAI-совместимый провайдер) вызывает инструменты мутации задач, получает пересчитанное расписание и формулирует ответ пользователю.
- **Excel-мост** — парсинг `.xlsx`-файлов (openpyxl) с поддержкой русских и английских названий колонок и экспорт готового расписания.
- **Реактивный фронтенд** — React 18 + TypeScript + Vite + Zod: трёхслойная защита от ошибок (сеть → HTTP → валидация), никаких белых экранов.
- **Observability Layer** — кастомная цветная система бизнес-логгирования на бэкенде. Позволяет в реальном времени видеть «мысли» LLM-агента, аргументы вызываемых инструментов и пошаговый каскадный пересчет графа планировщиком.
- **Интеллектуальный UX чата** — многострочное текстовое поле ввода, динамически подстраивающееся под размер текста с возможностью ручного вертикального ресайза (resize-y) без разрушения интерфейса.

## Архитектура и ключевые решения

### DAG Scheduler: единый источник дат

Модуль `backend/app/services/scheduler.py` — **единственное место** в системе, где вычисляются даты. Ни фронтенд, ни LLM-промпты не пересчитывают `startDate` и `endDate` вручную. Это архитектурный инвариант №1, нарушение которого немедленно ломает консистентность проекта.

- **Алгоритм Кана** (Kahn's algorithm) на `collections.defaultdict` + `collections.deque` — чистая стандартная библиотека Python, без зависимости от `networkx`.
- **Проверка циклов** через DFS по остаточному подграфу: если топологическая сортировка не покрыла все узлы — извлекается конкретный цикл и выбрасывается `CyclicDependencyError` с читаемым сообщением вида `"обнаружена циклическая зависимость: A -> B -> A"`.
- **Валидация ссылок:** дублирующиеся ID или ссылки на несуществующих предшественников → `ValueError` до построения графа.
- **Формула расчёта:** задача без предшественников стартует от `project_start_date` (по умолчанию — сегодня); задача с предшественниками стартует от `max(end_date предшественников)`; `end_date = start_date + timedelta(days=duration_days)`.
- **Транзакционность:** `TaskStore.set_raw_tasks()` сначала проверяет новый набор через `calculate_schedule()`, и только при успехе заменяет состояние. При ошибке (цикл, невалидные ссылки) состояние остаётся нетронутым.

### MCP-инструменты и Tool Calling Loop

Архитектура MCP (Model-Controller-Protocol) отделена от UI — каждый инструмент агностичен к фронтенду и оперирует только `RawTask[]`:

| Инструмент | Назначение | Атомарность |
|---|---|---|
| `update_task_details` | Частичное обновление полей задачи; `predecessors` — полная замена | Откат при ошибке |
| `add_new_task` | Создание задачи с автогенерацией `id` (`task-N`) | Проверка предшественников до создания |
| `delete_tasks` | Удаление одной или нескольких задач | Все или ничего; автоочистка осиротевших ссылок |

Поток Tool Calling (`backend/app/routers/chat.py`):
1. Сообщение пользователя + системный промпт → `llm_client.chat(messages, TOOL_DEFINITIONS)`
2. LLM возвращает `tool_calls` → бэкенд выполняет мутацию через `mcp_server.execute_tool_call()`
3. Результат (сводка изменённых задач в JSON) → обратно LLM для формирования ответа
4. Цикл повторяется до 5 раундов, пока LLM не вернёт финальный текст без tool calls
5. Пользователь получает `{ reply, tasks }` с пересчитанным расписанием

### In-Memory TaskStore

`TaskStore` — module-level singleton (`backend/app/services/task_store.py`), хранящий текущее состояние проекта:
- `_raw_tasks: list[RawTask]` — задачи без дат
- `_project_start_date: date` — базовая дата проекта
- Seed-данные (5 реалистичных задач) загружаются лениво при первом запросе
- Мутации транзакционны: ошибка графа не портит состояние

### Frontend: трёхслойная защита от ошибок

Фронтенд (`frontend/`) построен на React 18 + TypeScript + Vite + Zod:

- **Слой 1 — сеть:** `fetch` обёрнут в try/catch; при сетевой ошибке — понятное сообщение («Не удалось подключиться к серверу»).
- **Слой 2 — HTTP:** статусы 400/500 парсятся, извлекается `detail` из FastAPI `HTTPException`.
- **Слой 3 — Zod:** каждый ответ с задачами прогоняется через `z.array(GanttTaskSchema).parse()`. При `ZodError` — человекочитаемое перечисление проблем.

Все три слоя конвертируют ошибки в единый `Error`, который перехватывается на уровне `App.tsx` и показывается через `Toast` (автоскрытие 5 секунд). **Приложение никогда не падает белым экраном** (инвариант №3).

### Провайдерная гибкость LLM

Клиент `backend/app/services/llm_client.py` поддерживает два режима работы:

**1. OpenAI-совместимые API** (через `openai.AsyncOpenAI`):
- **OpenRouter** (`LLM_BASE_URL=https://openrouter.ai/api/v1`)
- **OpenAI** (`LLM_BASE_URL=https://api.openai.com/v1`)
- **DeepSeek** (`LLM_BASE_URL=https://api.deepseek.com/v1`)
- **Ollama** (локально: `LLM_BASE_URL=http://localhost:11434/v1`)
- **LM Studio**, **Groq**, и другие

**2. Google Gemini** (через официальный SDK `google-genai`):
- Автоматически активируется при наличии `"gemini"` в имени модели
- Требуется отдельный API-ключ: `GEMINI_API_KEY` (получить на https://aistudio.google.com/apikey)
- Поддерживаемые модели - все, которые поддерживаются API ключом. Проверить можно через google.py - вставив туда свой ключ. Идеально справляется с задачей gemini-3.1-flash-lite
- Автоматическая фильтрация полей `examples` из JSON-схем для совместимости с Gemini API
- Установка SDK: `pip install google-genai`

**Маршрутизация провайдера:**
```python

    # Используется google.genai.Client
else:
    # Используется openai.AsyncOpenAI
```

### Observability: Прозрачность работы AI-Агента

В систему внедрено кастомное структурированное логгирование с ANSI-раскраской в терминале бэкенда. Это позволяет полностью контролировать поведение LLM-модели и отслеживать корректность выполнения бизнес-логики:

- `[🤖 AI AGENT]` — логирует входящие промпты пользователя, шаги размышления модели и вызовы MCP-инструментов с их реальными аргументами.
- `[🔒 GUARD]` — логирует срабатывание систем защиты (включая автоматическое прерывание повторных вызовов одинаковых инструментов в рамках одного раунда Tool Loop).
- `[📊 DAG ENGINE]` — логирует работу математического движка, каскадные сдвиги дат и пересчет критического пути.

## Использование AI-ассистентов при разработке

Этот проект разработан по методологии **Prompt-Driven Architecture** — архитектура, инварианты и контракты данных были спроектированы человеком, а реализация делегирована AI-агентам под строгим контролем этих инвариантов.

### Как это работало

1. **Архитектурный каркас.** Сначала были созданы `architecture.md` и `system.md` — два документа, фиксирующих структуру папок, стек, контракты данных, потоки и пять критических инвариантов. Эти документы служили «конституцией» проекта: каждый AI-агент обязан был прочитать их перед внесением любого изменения.

2. **Декомпозиция на слои.** Разработка велась послойно:
   - **Слой контрактов:** Zod-схемы (`frontend/src/schemas/task.ts`) и Pydantic-модели (`backend/app/schemas/task.py`) — строгое зеркалирование полей, camelCase ↔ snake_case маппинг, русскоязычные `.describe()` / `Field(description=...)`.
   - **Слой сервисов:** DAG Scheduler (Kahn's algorithm + CyclicDependencyError), Excel-парсер (openpyxl с нормализацией заголовков), TaskStore (In-Memory с транзакционными мутациями).
   - **Слой инструментов:** MCP-инструменты (`update_task_details`, `add_new_task`, `delete_tasks`) — UI-агностичные функции с Pydantic-валидацией параметров.
   - **Слой интеграции:** LLM-клиент (OpenRouter → SDK `openai`), роутер чата с 5-раундовым Tool Calling Loop, API-роутер задач.
   - **Слой UI:** React-компоненты (GanttChart, ChatPanel, FileUpload, Toast) с трёхслойной защитой от ошибок.

3. **Иммутабельные инварианты.** Каждый агент перед написанием кода обязан был:
   - Перечитать `architecture.md` и `system.md`;
   - Написать план изменений;
   - Проверить план на соответствие 5 инвариантам;
   - Создать код с полной обработкой ошибок (Zod на фронте, Pydantic + HTTPException на бэке).

4. **Смоук-тесты на каждом шаге.** После создания каждого модуля запускался реальный Python-скрипт, проверяющий:
   - Корректность расчёта дат (известные цепочки задач с ожидаемыми датами);
   - Обнаружение циклов (A→B→A → `CyclicDependencyError`);
   - Транзакционный откат (попытка загрузить цикл → состояние не испорчено);
   - Круговой цикл Excel (создание → парсинг → scheduler → экспорт → повторный парсинг).

5. **Рефакторинг LLM-клиента.** Замена самописного `httpx` на официальный `openai.AsyncOpenAI` была проведена отдельным агентом с требованием сохранить сигнатуру `chat()` и все точки интеграции без изменений — ни одной правки в `chat_router.py` и `main.py`.

### Ключевой урок

Жёсткие архитектурные инварианты, зафиксированные до начала кодирования, оказались критически важны: они позволили распределить работу между несколькими AI-агентами без конфликтов и дрейфа архитектуры. Каждый агент работал в изолированном контексте своего слоя, опираясь на контракты из `architecture.md`, и мог независимо верифицировать свои изменения через смоук-тесты.

## Логика расчёта дат и диаграммы Гантта (DAG Engine)

### Математика планирования

DAG Scheduler вычисляет даты задач по следующим правилам:

#### 1. Параллельное выполнение (корневые задачи)

Если колонка «Предшественники» **пустая**, задача является **корневой** и стартует в базовый день старта проекта:

$$
\text{start\_date}(A) = \text{project\_start\_date}
$$

$$
\text{end\_date}(A) = \text{start\_date}(A) + \text{duration\_days}(A)
$$

**Пример:** если в проекте есть две задачи без предшественников (A и B), они выполняются **одновременно**, накладываясь на диаграмме:

```
День 1-5:  [A: Анализ требований] (5 дней)
День 1-3:  [B: Исследование]       (3 дня, ПАРАЛЛЕЛЬНО с A)
```

#### 2. Последовательные зависимости (Finish-to-Start)

Если указан один предшественник `N`, задача стартует **на следующий день после завершения** задачи `N`:

$$
\text{start\_date}(C) = \text{end\_date}(N)
$$

$$
\text{end\_date}(C) = \text{start\_date}(C) + \text{duration\_days}(C)
$$

**Пример:** задача C зависит от задачи A (длительность 5 дней, даты 1-5 августа):

```
A: День 1-5    [Анализ требований]
C: День 6-9    [Проектирование БД] (старт = end_date(A) = 6 августа)
```

#### 3. Множественные зависимости (слияние веток)

Если указано несколько предшественников `N₁, N₂, …, Nₖ`, дата старта рассчитывается как:

$$
\text{start\_date}(E) = \max(\text{end\_date}(N₁), \text{end\_date}(N₂), \ldots, \text{end\_date}(Nₖ))
$$

Задача **ждёт завершения ВСЕХ** предшественников и стартует после самого позднего из них.

**Пример:** задача E зависит от C и D:

```
C: День 6-9    [Проектирование БД] (end_date = 9)
D: День 4-7    [UI-макеты]         (end_date = 7)
E: День 10-12  [Тестирование]      (старт = max(9, 7) = 10)
```

### Граф зависимостей

Шаблон Excel демонстрирует все типы связей на примере 5 задач:


### Алгоритм Кана (топологическая сортировка)

`scheduler.py` использует **алгоритм Кана** для определения порядка расчёта дат:

1. **Строится граф:** каждая задача — узел, каждая зависимость `predecessors` — направленное ребро.
2. **Вычисляется входящая степень** (in-degree): число предшественников для каждой задачи.
3. **Инициализация очереди:** все узлы с `in_degree = 0` (корневые задачи) добавляются в очередь.
4. **Обход:**
   - Извлечь узел из очереди → рассчитать его даты.
   - Для каждого соседа (зависимой задачи) уменьшить `in_degree` на 1.
   - Если `in_degree` соседа стал 0 → добавить в очередь.
5. **Проверка циклов:** если обработаны не все узлы → остаток содержит цикл → `CyclicDependencyError`.

**Преимущества Кана:**
- Гарантирует, что предшественники обрабатываются раньше зависимых задач.
- Детерминированный порядок (задачи обрабатываются в порядке исходного списка при равных условиях).
- $O(V + E)$ — линейная сложность по числу задач и зависимостей.

### Обнаружение и блокировка циклов

Циклическая зависимость (A → B → A) делает расчёт дат невозможным. Scheduler обнаруживает циклы через DFS по остаточному подграфу:

```python
if len(topological_order) != len(tasks):
    unprocessed = [задачи, не вошедшие в топологический порядок]
    cycle = _find_cycle_dfs(unprocessed)
    raise CyclicDependencyError(cycle)
```

**Пример ошибки:**
```
CyclicDependencyError: Обнаружена циклическая зависимость между задачами:
task-2 -> task-3 -> task-2. Устраните цикл в поле predecessors.
```

Мутация **откатывается** — состояние `TaskStore` остаётся консистентным.

### Редактирование через AI-чат

Пользователь может смещать даты задач через естественный язык:

```
User: Сдвинь Задачу 3 так, чтобы она начиналась 10 августа
```

LLM вызовет инструмент `update_task_details` для корректировки предшественников или длительности, после чего **весь граф пересчитывается автоматически**, сохраняя зависимости.

**Важно:** прямое указание дат невозможно — изменяются только `duration_days` и `predecessors`. Scheduler гарантирует, что все зависимые задачи сдвинутся корректно.

Тестовый фреймворк на базе `pytest` эмулирует реальные сессии чата и проверяет атомарность изменений, транзакционные откаты стейта хранилища и прохождение полного цикла вызовов инструментов (`Tool Calling Loop`).

### 🧪 4 Ключевых сценария для проверки системы:

1. **Генерация стартового пула задач (из пустой таблицы):**
   - **Промпт:** Спланируй проект «Разработка MVP моб приложения» на 6 последовательных задач с 10 августа 2026 года (Исполнители: Анна, Дмитрий, Сергей, Ирина, Семён, Елена).
   - **Что проверяется:** Способность модели за один раунд без галлюцинаций сгенерировать правильную JSON-структуру, провязать последовательную цепочку `predecessors` (`task-1 -> task-2 -> ...`) и корректно рассчитать финальную дату релиза.

2. **Разветвление графа на параллельные ветки (Слияние треков):**
   - **Промпт:** Сделай так, чтобы «Разработка API» и «Верстка UI» выполнялись параллельно от «Архитектура БД», а «Тестирование» началось строго после завершения обеих задач.
   - **Что проверяется:** Нарушение линейной структуры графа, запись множественного предка в массив `predecessors: ["task-4", "task-5"]` у задачи Тестирования и выбор планировщиком максимальной даты окончания (`max(End_API, End_UI)`) для старта последующих этапов.

3. **Добавление независимой задачи с произвольной датой (`preferred_start_date`):**
   - **Промпт:** Добавь независимую задачу «Подготовка маркетинг-материалов» на 5 дней с датой начала 12 августа. Исполнитель Анна.
   - **Что проверяется:** Корректная обработка жёстких ограничений пользователя. Новая задача должна наложиться на график параллельно разработке, не имея связей с основным инженерным треком и не ломая текущие зависимости.

   - **Что проверяется:** Реактивность системы. Имя исполнителя на одной ветке мгновенно меняется, а увеличение длительности на критическом пути автоматически сдвигает все последующие даты графа и финальный релиз вправо в реальном времени.

### Тестирование и Evals

Тесты агента построены на **Evals** — автоматическом прогоне сценариев, записанных на основе реальных вызовов тулов и ответов LLM. Это позволяет изолировать логику агента, находить рассинхроны в стейте и отлаживать ошибки `Tool Calling Loop` на реальных данных.

#### 1. Запуск тестов

```bash
cd backend
python -m pytest tests/test_agent_evals.py -v
```

2. Добавление нового Eval-кейса из логов
Если при работе с агентом возникла ошибка или нетипичное поведение, сценарий можно быстро превратить в регрессионный тест:

Открой папку логов за нужную дату (backend/logs/YYYY-MM-DD/).

Найди JSON-файл нужного вызова (например, 12-20-51_update_task_details.json).

3. Скопируй этот лог в папку кейсов backend/tests/eval_cases/

Windows (PowerShell):
```bash
Copy-Item backend\logs\2026-08-03\12-20-51_update_task_details.json backend\tests\eval_cases\
```

Linux / macOS:
```bash
cp backend/logs/2026-08-03/12-20-51_update_task_details.json backend/tests/eval_cases/
```

4. Запусти pytest заново

```bash
python -m pytest tests/test_agent_evals.py -v
```
тесты автоматически пройдутся по всем .json в папке,
воспроизведут входной запрос и подсветят расхождения в генерации или обновлении табличного состояния.
