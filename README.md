# AI-Native Gantt Chart

**Интерактивное управление проектами с AI-ассистентом и DAG-планировщиком.** Загрузка диаграммы Гантта из Excel, автоматический расчёт дат с учётом зависимостей, диалоговое управление задачами через чат с LLM — и всё это без единой ручной перестановки сроков.

---

## Обзор

AI-Native Gantt Chart — это веб-приложение, в котором диаграмма Гантта является не просто визуализацией, а живым объектом, управляемым AI. Вы говорите ассистенту «увеличь длительность разработки API до 10 дней» — и задачи пересчитываются с учётом графа зависимостей. Вы загружаете Excel-файл со списком задач — и получаете готовое расписание за секунды.

**Ключевые компоненты:**

- **DAG Scheduler** — ядро планирования: топологическая сортировка (алгоритм Кана), математический расчёт всех дат, обнаружение и блокировка циклических зависимостей.
- **LLM Tool Calling Loop** — 5-раундовый цикл, в котором LLM через OpenRouter (или любой OpenAI-совместимый провайдер) вызывает инструменты мутации задач, получает пересчитанное расписание и формулирует ответ пользователю.
- **Excel-мост** — парсинг `.xlsx`-файлов (openpyxl) с поддержкой русских и английских названий колонок и экспорт готового расписания.
- **Реактивный фронтенд** — React 18 + TypeScript + Vite + Zod: трёхслойная защита от ошибок (сеть → HTTP → валидация), никаких белых экранов.

## Архитектура и ключевые решения

### DAG Scheduler: единый источник дат

Модуль `backend/app/services/scheduler.py` — **единственное место** в системе, где вычисляются даты. Ни фронтенд, ни LLM-промпты не пересчитывают `startDate` и `endDate` вручную. Это архитектурный инвариант №1, нарушение которого немедленно ломает консистентность проекта.

- **Алгоритм Кана** (Kahn's algorithm) на `collections.defaultdict` + `collections.deque` — чистая стандартная библиотека Python, без зависимости от `networkx`.
- **Проверка циклов** через DFS по остаточному подграфу: если топологическая сортировка не покрыла все узлы — извлекается конкретный цикл и выбрасывается `CyclicDependencyError` с читаемым сообщением вида `"обнаружена циклическая зависимость: A -> B -> A"`.
- **Валидация ссылок:** дублирующиеся ID или ссылки на несуществующих предшественников → `ValueError` до построения графа.
- **Формула расчёта:** задача без предшественников стартует от `project_start_date` (по умолчанию — сегодня); задача с предшественниками стартует от `max(end_date предшественников)`; `end_date = start_date + timedelta(days=duration_days)`.
- **Транзакционность:** `TaskStore.set_raw_tasks()` сначала проверяет новый набор через `calculate_schedule()`, и только при успехе заменяет состояние. При ошибке (цикл, невалидные ссылки) состояние остаётся нетронутым.

### MCP-инструменты и Tool Calling Loop

Архитектура MCP (Model-Controller-Protocol) отделена от UI — каждый инструмент агностичен к фронтенду и оперирует только `RawTask[]`:

| Инструмент | Назначение | Атомарность |
|---|---|---|
| `update_task_details` | Частичное обновление полей задачи; `predecessors` — полная замена | Откат при ошибке |
| `add_new_task` | Создание задачи с автогенерацией `id` (`task-N`) | Проверка предшественников до создания |
| `delete_tasks` | Удаление одной или нескольких задач | Все или ничего; автоочистка осиротевших ссылок |

Поток Tool Calling (`backend/app/routers/chat.py`):
1. Сообщение пользователя + системный промпт → `llm_client.chat(messages, TOOL_DEFINITIONS)`
2. LLM возвращает `tool_calls` → бэкенд выполняет мутацию через `mcp_server.execute_tool_call()`
3. Результат (сводка изменённых задач в JSON) → обратно LLM для формирования ответа
4. Цикл повторяется до 5 раундов, пока LLM не вернёт финальный текст без tool calls
5. Пользователь получает `{ reply, tasks }` с пересчитанным расписанием

### In-Memory TaskStore

`TaskStore` — module-level singleton (`backend/app/services/task_store.py`), хранящий текущее состояние проекта:
- `_raw_tasks: list[RawTask]` — задачи без дат
- `_project_start_date: date` — базовая дата проекта
- Seed-данные (5 реалистичных задач) загружаются лениво при первом запросе
- Мутации транзакционны: ошибка графа не портит состояние

### Frontend: трёхслойная защита от ошибок

Фронтенд (`frontend/`) построен на React 18 + TypeScript + Vite + Zod:

- **Слой 1 — сеть:** `fetch` обёрнут в try/catch; при сетевой ошибке — понятное сообщение («Не удалось подключиться к серверу»).
- **Слой 2 — HTTP:** статусы 400/500 парсятся, извлекается `detail` из FastAPI `HTTPException`.
- **Слой 3 — Zod:** каждый ответ с задачами прогоняется через `z.array(GanttTaskSchema).parse()`. При `ZodError` — человекочитаемое перечисление проблем.

Все три слоя конвертируют ошибки в единый `Error`, который перехватывается на уровне `App.tsx` и показывается через `Toast` (автоскрытие 5 секунд). **Приложение никогда не падает белым экраном** (инвариант №3).

### Провайдерная гибкость LLM

Клиент `backend/app/services/llm_client.py` построен на официальном SDK `openai.AsyncOpenAI`, поэтому работает с любым OpenAI-совместимым API:
- **OpenRouter** (`LLM_BASE_URL=https://openrouter.ai/api/v1`)
- **OpenAI** (`LLM_BASE_URL=https://api.openai.com/v1`)
- **DeepSeek** (`LLM_BASE_URL=https://api.deepseek.com/v1`)
- **Ollama** (локально: `LLM_BASE_URL=http://localhost:11434/v1`)
- **LM Studio**, **Groq**, и другие

## Быстрый старт

### 1. Клонирование и зависимости

```bash
git clone <repo-url>
cd bioteh

# Бэкенд
cd backend
pip install fastapi uvicorn pydantic openai openpyxl python-dotenv

# Фронтенд
cd ../frontend
npm install
```

### 2. Конфигурация — файл `.env`

Создайте `backend/.env` с **одним** из вариантов ниже:

```bash
# === OpenRouter (рекомендуется) ===
LLM_API_KEY=sk-or-v1-ваш-ключ
LLM_MODEL=deepseek/deepseek-chat
LLM_BASE_URL=https://openrouter.ai/api/v1

# === OpenAI ===
# LLM_API_KEY=sk-ваш-ключ
# LLM_MODEL=gpt-4o-mini
# LLM_BASE_URL=https://api.openai.com/v1

# === DeepSeek ===
# LLM_API_KEY=sk-ваш-ключ
# LLM_MODEL=deepseek-chat
# LLM_BASE_URL=https://api.deepseek.com/v1

# === Ollama (локально) ===
# LLM_API_KEY=ollama
# LLM_MODEL=llama3.2
# LLM_BASE_URL=http://localhost:11434/v1

# Лимит токенов ответа (опционально, default 4096)
LLM_MAX_TOKENS=4096
```

> **Примечание:** для обратной совместимости также поддерживаются переменные `OPENROUTER_API_KEY`, `OPENROUTER_MODEL` и `OPENROUTER_BASE_URL`.

### 3. Запуск

**Терминал 1 — бэкенд (порт 8000):**
```bash
cd backend
uvicorn app.main:app --app-dir . --reload --host 0.0.0.0 --port 8000
```

**Терминал 2 — фронтенд (порт 5173):**
```bash
cd frontend
npm run dev
```

Откройте `http://localhost:5173`. Приложение загрузит seed-данные (5 задач с реалистичными зависимостями) и отобразит диаграмму Гантта.

### 4. Первые шаги

- **Загрузите свой Excel** — нажмите «Загрузить Excel» и выберите `.xlsx`-файл с задачами. Поддерживаются русские и английские названия колонок: «Задача»/«Title», «Описание»/«Description», «Длительность»/«Duration_days», «Предшественники»/«Predecessors».
- **Скачайте расписание** — нажмите «Скачать Excel» для экспорта текущего плана с датами.
- **Поговорите с AI** — в поле чата справа напишите, например: «Увеличь длительность задачи task-3 до 10 дней» или «Добавь задачу Код-ревью после Разработки API». AI вызовет нужные инструменты и вернёт обновлённую диаграмму.

### API (для справки)

| Метод | Путь | Описание |
|---|---|---|
| `GET` | `/api/tasks` | Список всех задач с датами (seed при первом запросе) |
| `POST` | `/api/tasks/upload` | Загрузка Excel-файла, замена проекта |
| `GET` | `/api/tasks/export` | Скачать текущее расписание как `.xlsx` |
| `POST` | `/api/chat` | Отправить сообщение AI-ассистенту |
| `GET` | `/api/health` | Проверка доступности сервера |

## Использование AI-ассистентов при разработке

Этот проект разработан по методологии **Prompt-Driven Architecture** — архитектура, инварианты и контракты данных были спроектированы человеком, а реализация делегирована AI-агентам под строгим контролем этих инвариантов.

### Как это работало

1. **Архитектурный каркас.** Сначала были созданы `architecture.md` и `system.md` — два документа, фиксирующих структуру папок, стек, контракты данных, потоки и пять критических инвариантов. Эти документы служили «конституцией» проекта: каждый AI-агент обязан был прочитать их перед внесением любого изменения.

2. **Декомпозиция на слои.** Разработка велась послойно:
   - **Слой контрактов:** Zod-схемы (`frontend/src/schemas/task.ts`) и Pydantic-модели (`backend/app/schemas/task.py`) — строгое зеркалирование полей, camelCase ↔ snake_case маппинг, русскоязычные `.describe()` / `Field(description=...)`.
   - **Слой сервисов:** DAG Scheduler (Kahn's algorithm + CyclicDependencyError), Excel-парсер (openpyxl с нормализацией заголовков), TaskStore (In-Memory с транзакционными мутациями).
   - **Слой инструментов:** MCP-инструменты (`update_task_details`, `add_new_task`, `delete_tasks`) — UI-агностичные функции с Pydantic-валидацией параметров.
   - **Слой интеграции:** LLM-клиент (OpenRouter → SDK `openai`), роутер чата с 5-раундовым Tool Calling Loop, API-роутер задач.
   - **Слой UI:** React-компоненты (GanttChart, ChatPanel, FileUpload, Toast) с трёхслойной защитой от ошибок.

3. **Иммутабельные инварианты.** Каждый агент перед написанием кода обязан был:
   - Перечитать `architecture.md` и `system.md`;
   - Написать план изменений;
   - Проверить план на соответствие 5 инвариантам;
   - Создать код с полной обработкой ошибок (Zod на фронте, Pydantic + HTTPException на бэке).

4. **Смоук-тесты на каждом шаге.** После создания каждого модуля запускался реальный Python-скрипт, проверяющий:
   - Корректность расчёта дат (известные цепочки задач с ожидаемыми датами);
   - Обнаружение циклов (A→B→A → `CyclicDependencyError`);
   - Транзакционный откат (попытка загрузить цикл → состояние не испорчено);
   - Круговой цикл Excel (создание → парсинг → scheduler → экспорт → повторный парсинг).

5. **Рефакторинг LLM-клиента.** Замена самописного `httpx` на официальный `openai.AsyncOpenAI` была проведена отдельным агентом с требованием сохранить сигнатуру `chat()` и все точки интеграции без изменений — ни одной правки в `chat_router.py` и `main.py`.

### Ключевой урок

Жёсткие архитектурные инварианты, зафиксированные до начала кодирования, оказались критически важны: они позволили распределить работу между несколькими AI-агентами без конфликтов и дрейфа архитектуры. Каждый агент работал в изолированном контексте своего слоя, опираясь на контракты из `architecture.md`, и мог независимо верифицировать свои изменения через смоук-тесты.
